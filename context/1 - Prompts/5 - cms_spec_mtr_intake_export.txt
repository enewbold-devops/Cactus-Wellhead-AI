Got it — in your MTR Intake flow, the **CMS Specification** becomes the “source of truth” that every submitted MTR (and any supplemental lab report) is validated against.

In the Cactus Wellhead context, the CMS specs are typically **controlled internal specifications** (revisioned documents inside the QMS) that sit alongside API/ISO requirements (Cactus explicitly references an API Spec 6A + Q1/ISO 9001:2015 QMS) and drive supplier conformance, special processes, and reporting (they even publish an “approved sub-supplier” list referencing internal process/spec codes like CST-801, CST-811, etc.).

Below is a practical way to **discover/speciate CMS specs by category** and then a **data model** that supports a *range* of CMS specifications (materials, parts, tools), including the chemical/mechanical/Charpy/HT/hardness patterns you’ve been driving.

---

## 1) Discover and classify CMS specifications for MTR Intake

### A. Build a CMS “spec registry” first (one row per spec revision)
Create an authoritative inventory of *all* CMS documents that can be referenced by suppliers or QA:
- **Spec Code** (ex: `CMS-MTL-…`, `CMS-HT-…`, `CST-801`-style process codes, etc.)
- **Title**
- **Category**: Material / Part / Tool (details below)
- **Applies To**: product line, component family, pressure class, service (H2S/NACE), etc.
- **Governing external standards**: API 6A, ASTM/ASME, NACE, ISO, etc. (as references)
- **Revision + effective date + approver** (QMS control)
- **Supplier submission requirements**: required report types, required fields, required attachments

This registry is what your MTR intake uses to decide “**what ruleset applies**.”

### B. Create a 3-level taxonomy: Category → Subcategory → Spec Family
You’ll discover specs fastest if you classify them like this:

**1) Material CMS specs**
- **Alloy/grade requirements** (chemical composition ranges)
- **Mechanical properties** (YS/UTS/Elong/RA, etc.)
- **Impact toughness** (Charpy V-notch requirements by temperature/orientation/location)
- **Heat treatment requirements** (normalize, quench & temper, PWHT, carburize/nitride, etc.) — often tied to approved processor lists
- **Hardness requirements** (HB/HRC/HV; max/min; conversion rules; location rules)
- **Cleanliness / microstructure / grain size** (if applicable)
- **NDE requirements** (UT/MT/PT, acceptance criteria)
- **Traceability requirements** (heat/lot, product form, size range, heat number, etc.)

**2) Part CMS specs**
- “Material + process + inspection” bundled to a part number or drawing:
  - part material spec reference
  - machining + dimensional inspection plan
  - coating/plating spec reference
  - functional tests (pressure tests, etc.)
  - marking/serialization/traceability
  - repair/refurb acceptance (if serviced equipment)

**3) Tool CMS specs**
- Tools/fixtures/gauges used in manufacturing or inspection:
  - calibration and metrology requirements (intervals, as-found/as-left, tolerance bands)
  - measurement system capability (gage R&R, uncertainty)
  - tool material (if relevant) and wear limits
  - storage/handling requirements
  - special-process tooling constraints (if used in nitriding, plating, etc.)

## 2) “Range of CMS specs” — what your data model must support

To validate MTRs in an automated/consistent way, each CMS spec needs to encode **testable requirements** as structured rules, not just PDF text.

At minimum, each spec should be expressible as:
- **Required tests** (what must be present)
- **Acceptance limits** (min/max/target ranges)
- **Conditional logic** (depends on thickness, product form, temperature class, service environment, etc.)
- **Sampling rules** (how many tests per heat/lot; locations/orientation)
- **Units + conversions** (ksi↔MPa; °F↔°C; HRC↔HB conversions allowed or prohibited)
- **Document evidence requirements** (EN 10204 3.1 / 3.2, lab accreditation, cert statements)

---

## 3) Data model for CMS Specifications (designed for MTR Intake validation)

### Core entities (works for Material, Part, Tool)
1) **CMS_Specification**
- `SpecId` (GUID)
- `SpecCode` (string)
- `Title`
- `Category` (Material | Part | Tool)
- `Status` (Draft/Released/Obsolete)
- `OwnerOrg` (Engineering/QA/etc.)
- `Description`
- `GoverningStandards[]` (links)

2) **CMS_SpecRevision**
- `SpecRevisionId`
- `SpecId` (FK)
- `Revision` (e.g., “Rev F”)
- `EffectiveDate`, `SupersedesRevisionId`
- `ApprovedBy`, `ApprovedDate`
- `DocumentLink` (PDF/file pointer)
- `ChangeSummary`
- `AppliesToConstraints` (structured: product lines, size ranges, service class)

3) **CMS_RequirementSet**
A revision can have multiple requirement sets (because rules differ by context).
- `RequirementSetId`
- `SpecRevisionId` (FK)
- `Name` (e.g., “Q&T forgings ≤ 6 in thick”, “NACE sour service”)
- `ConditionExpression` (rule expression evaluated by intake engine)

4) **CMS_TestRequirement**
- `TestReqId`
- `RequirementSetId` (FK)
- `TestType` (Chemistry | Tensile | Charpy | Hardness | HeatTreat | NDE | Dimensional | Coating | Calibration | FunctionalTest)
- `StandardMethod` (ASTM A370, E23, E18, etc.)
- `SamplingPlan` (structured)
- `EvidenceType` (MTR field, lab report, chart, calibration cert)

5) **CMS_AcceptanceCriterion**
A test requirement can have multiple criteria.
- `CriterionId`
- `TestReqId` (FK)
- `Property` (e.g., “C”, “Mn”, “YS”, “UTS”, “Elong”, “CVN_Avg”, “HRC”, “TemperTemp”, “CaseDepth”)
- `MinValue`, `MaxValue`, `TargetValue`
- `Units`
- `PrecisionRule` (rounding, sig figs)
- `LocationRule` (where on the part / specimen orientation)
- `Notes`

6) **CMS_ProcessRequirement** (for special processes like heat treat, nitriding, coatings)
- `ProcessReqId`
- `RequirementSetId`
- `ProcessType` (HeatTreat, Nitriding, Plating, Coating, Welding, etc.)
- `ApprovedSupplierRequired` (bool)
- `ApprovedSupplierListRef` (links to list like the published “Approved Sub-Suppliers” doc)
- `ProcessParameters[]` (structured limits: temp/time/quench media, etc.)
- `PostProcessTests[]` (links back to TestRequirements)

7) **CMS_DocumentRequirement**
- `DocReqId`
- `RequirementSetId`
- `DocumentType` (EN10204-3.1, Certificate of Conformance, Heat Treat Chart, NDE report, Calibration cert)
- `RequiredFields[]`
- `MustMatchFields[]` (traceability bindings: heat number, PO, part no.)

---

## 4) How MTR Intake uses this model (high-level validation flow)

When an MTR comes in:
1) Identify **SpecRevision** from: part number → part spec → material spec (or supplier-provided spec code).
2) Evaluate which **RequirementSet(s)** apply (thickness, service class, product form, etc.).
3) For each **TestRequirement**:
   - Confirm test exists in the submission (fields + attachments).
   - Validate each **AcceptanceCriterion** (units, conversions, rounding).
4) Validate **traceability joins** (heat/lot → part serial → PO line → manufacturer).
5) Validate **special processes** used are allowed + (if required) performed by an approved sub-supplier.
6) Produce an auditable outcome: Pass / Fail / Pass-with-Deviation (if your QMS allows) and a findings report aligned to the CMS criteria.

## 5) Example JSON shape for a CMS requirement set (so you can store + execute rules)

{
  "specCode": "CMS-MTL-4130-QT",
  "revision": "Rev D",
  "category": "Material",
  "requirementSet": {
    "name": "Q&T forging, thickness <= 6.0 in, sour service = false",
    "condition": "productForm == 'FORGING' && thickness_in <= 6.0 && sourService == false",
    "tests": [
      {
        "testType": "Chemistry",
        "method": "ASTM E415",
        "criteria": [
          { "property": "C", "min": 0.28, "max": 0.33, "units": "wt_pct" },
          { "property": "Cr", "min": 0.80, "max": 1.10, "units": "wt_pct" }
        ]
      }
    ],
    "documentRequirements": [
      { "type": "EN10204_3_1", "required": true },
      { "type": "HeatTreatChart", "required": true }
    ]
  }
}
