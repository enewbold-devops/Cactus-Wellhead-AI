Absolutely — here’s a solid end-to-end intake workflow Cactus can use to validate incoming MTRs (Mill Test Reports) from customers or suppliers, with the checkpoints that typically matter for pressure-control / wellhead hardware (chemistry, mechanicals, Charpy, heat treat, hardness, traceability, and calibration references).

1) Intake and Gate-0 Triage
Trigger: customer sends an MTR for incoming material, or supplier ships material with an MTR packet.
Gate-0 objective: ensure the packet is complete enough to evaluate.

Required intake artifacts (minimum):
- MTR (CMTR if required) with:
  - Heat number / cast number
  - Product form (bar, forging, plate, tubular, casting)
  - Spec / grade (ASTM/ASME/API + any customer spec)
  - Quantity, size, and PO / line item reference
- Packing list / CoC / shipment reference
- Traceability docs (if applicable): melt source, forging/casting route, re-melt (ESR/VAR), NDE certs
- Any customer-specific deviations/waivers already approved (if any)

Outcome:
- Pass: create an “MTR Validation Case” record (internal tracking ID).
- Fail: return to sender as “incomplete packet” with a punch list.

2) Identity, Traceability, and Scope Check
Objective: confirm the MTR actually corresponds to the material on the PO and shipment.

Checks:
- Heat number on MTR matches:
  - packing list
  - physical markings (heat stamp / tag / bundle ID)
  - receiving record
- Product form and dimensions match PO + receiving inspection
- Spec/grade matches the PO line (and any flowdown requirements)

Typical rejection reasons:
- Heat number mismatch
- Wrong grade (e.g., AISI 4130 vs 4140, or different PSL/trim expectation)
- MTR covers “similar” heats or multiple heats without clear segregation

3) Standards & Customer Flowdown Requirements Mapping
Objective: translate customer requirements into a validation checklist.

Inputs:
- Cactus master spec (material class rules, test frequency, acceptance criteria)
- Customer engineering spec / datasheet
- Applicable code/standard references (ASTM/ASME/API/NACE/ISO, etc.)

Output artifact:
- “Requirements Map” (a structured checklist):
  - Chemistry limits
  - Mechanical minima/maxima
  - Impact (Charpy) requirements (temp, orientation, specimen size, location)
  - Heat treatment method + parameters + acceptance windows
  - Hardness limits + scale + conversion rules
  - Test frequency / lot definition (heat/lot/batch)
  - Supplementary requirements (NDE, grain size, decarb, cleanliness, sour service)

4) Chemistry Validation
Objective: confirm reported chemistry is compliant and appropriate for service.

Checks:
- All required elements reported (not just “major” elements)
- Values within min/max for the governing spec and customer flowdown
- Carbon equivalent (if required) calculated and compliant
- If sour service / SSC concerns exist:
  - confirm chemistry supports hardness limits and heat treat route
  - confirm any NACE/ISO 15156 / MR0175 flowdowns (if specified by the customer)

Outcome:
- Pass / Conditional (needs clarification) / Reject

5) Mechanical Properties Validation
Objective: confirm tensile/yield/elongation/RA meet requirements.

Checks:
- Test standard used (ASTM A370, etc.) listed
- Test location is correct for product form (e.g., forging mid-radius vs bar center)
- Values meet minima, and do not exceed maxima if customer caps exist
- Heat treat condition on the tensile test matches the material’s delivered condition

Common issues:
- Tensile results “look good” but were taken from the wrong location or condition
- Missing reduction of area (RA) when required

6) Impact (Charpy) Validation (when required)
Objective: confirm impact toughness matches customer/service expectations.

Checks:
- Test temperature matches requirement (e.g., -50°F / -46°C / etc.)
- Orientation (L-T, T-L) and notch direction documented
- Specimen size documented (full-size vs sub-size) and acceptance criteria applied correctly
- Number of specimens and averaging rules compliant
- Location of sample (thickness position, forging zone) compliant

Outcome:
- Pass / Conditional (needs raw data or specimen details) / Reject

7) Heat Treatment Validation
Objective: confirm the heat treat route supports the required properties and is documented.

Checks:
- Process type: Q&T / normalize & temper / solution anneal & age / etc.
- Actual parameters recorded:
  - austenitize / solution temp & soak
  - quench medium (oil/water/polymer/air) as applicable
  - temper temp/time (often the biggest scrutiny item)
- Lot definition and furnace load traceability
- Furnace calibration references (where applicable) and compliance statement

Red flags:
- Only “Heat treated per spec” with no temps/times when customer requires actuals
- No linkage between furnace run and heat/lot

8) Hardness Validation
Objective: verify hardness meets limits and that the method/scale is acceptable.

Checks:
- Hardness scale (HRC/HB/HV) and method (Rockwell/Brinell/Vickers)
- Location(s) and sampling plan
- Conversion rules (only if allowed; otherwise reject “converted only” values)
- Compliance with customer hardness maxima (especially for sour service)

9) Conformance Decision + Disposition
Decision states:
- Accepted (full compliance)
- Accepted with Conditions (minor clarifications, doc corrections, supplier revision required)
- Rejected (nonconforming material or unverifiable certification)
- Deviation Required (engineering/customer waiver needed)

Artifacts produced:
- MTR Validation Report (internal): pass/fail by requirement line
- Supplier Corrective Action / punch list (if conditional/reject)
- Deviation request package (if waiver path)

10) Records Control and Traceability Lockdown
Objective: make the MTR “bind” to the material in Cactus systems.

Actions:
- Store the approved MTR packet in controlled repository (revision locked)
- Link MTR to:
  - PO line
  - heat/lot record
  - receiving inspection lot
  - future WIP traveler / router (so the same heat number persists through machining, HT, coating, assembly)
- If re-certification or re-testing occurs, ensure:
  - original MTR retained
  - addendum is clearly marked and traceable

Practical “Who Does What” (Typical RACI)
- Receiving QC: Gate-0 completeness + identity/heat trace
- Materials/Metallurgy/QE: chemistry, mechanical, Charpy, HT, hardness evaluation
- Engineering: disposition when requirements interpretation is needed
- Quality Manager: approve deviations / supplier NCRs / final release rules
- Document Control: records retention + revision control

1) CRM record types you need (minimum viable)

A) MTR Validation Case (the “work item” in queues)
Purpose: one record per material lot/heat/line-item that must be validated.

Key fields (customer/supplier provided)
- Counterparty Type: Customer | Supplier
- Counterparty Account (lookup)
- PO Number + PO Line (or Customer Order / Sales Order + Line)
- Part / Item Number (Cactus internal) + Description
- Material Spec / Grade (as-stated on MTR)
- Product Form: bar / forging / casting / plate / tubular
- Heat Number / Cast Number (critical)
- Quantity + Dimensions
- Intended Service / Program (if applicable): e.g., “sour”, “low temp”, “PSL level”, etc.
- Required Standards (multi-select / related table): API/ASTM/ASME/NACE/ISO references
- Due Date (often tied to receiving need-by or build schedule)
- Status (workflow state): see section 3

Key internal linkage fields
- Internal Lot/Batch ID (receiving lot)
- Traveler / Router ID (if in MES/ERP)
- NCR/Deviation IDs (if created)
- Approved MTR Revision pointer (document control link)

B) MTR Document (the “packet”)
Purpose: store the files and extract/record the important metadata.

Fields:
- Document Type: MTR / CMTR / CoC / NDE / HT chart / Hardness map / etc.
- Supplier/Customer Document ID (if present)
- Report Date
- Revision / Version
- Heat Number(s) referenced (ideally structured as a child list if multiple heats)
- Source (email/portal/upload)
- File(s) (attachments) + checksum/hash optional
- “Parsed?” boolean + confidence (if you later automate extraction)

C) Requirements Map (what Cactus must validate against)
Purpose: ties “what is required” to “what is provided” and prevents tribal-knowledge decisions.

Fields:
- Governing Spec (e.g., ASTM A29 / A182 / API 6A + customer spec)
- Requirement Set Version (internal rev)
- Service modifiers: Sour? Low temp? PSL? etc.
- Required tests: Chem / Tensile / Charpy / Hardness / HT parameters / NDE / etc.

D) Validation Checklist Items (line-by-line pass/fail)
Purpose: the auditable record of why something passed.

Fields:
- Category: Chemistry / Mechanical / Charpy / Heat Treat / Hardness / Traceability / NDE / Docs
- Requirement statement (text)
- Acceptance criteria (structured where possible: min/max, temp, specimen size)
- Result value(s) + units
- Pass/Fail/Conditional
- Reviewer + timestamp
- Comment / rationale
- Evidence pointer (link to page/section of document)

2) The intake → queue routing logic (how it becomes a CRM “queue item”)
When an MTR packet arrives (email upload, portal, EDI, etc.), CRM should:
1) Create/Update Counterparty (Customer/Supplier account)
2) Create MTR Validation Case
3) Attach MTR Document(s)
4) Auto-build the Requirements Map (based on part/material/service/program)
5) Generate Checklist Items (templated from Requirements Map)
6) Route the Case to the correct queue based on rules below

Routing rules (examples)
- If Heat # missing / mismatch → Intake – Traceability Exception Queue
- If spec/grade differs from PO → Quality – Spec Mismatch Queue
- If Charpy required → Metallurgy – Impact Review Queue
- If sour-service hardness caps apply → Metallurgy – Sour Service Queue
- If missing test data → Supplier/Customer Clarification Queue
- If everything present → QE Review Queue (normal flow)

3) Case status model that matches real work
Use statuses that match gates (so queues stay clean):
1. New – Untriaged
2. Pending Packet Completeness
3. Traceability Review
4. Requirements Mapping
5. Technical Validation In Progress
6. Pending Clarification (External)
7. Pending Deviation/Waiver
8. Accepted

Add a parallel field “Stop-Ship / Stop-Use” flag for high-risk cases.

4) What “key customer/supplier info” is necessary (so validation can be automated and auditable)
Think in 3 layers: Identity, Requirements, Evidence.

Identity (must-have)
- Counterparty name + site (some suppliers have multiple mills)
- PO + line, part number
- Heat number / cast number
- Product form + size
- Quantity + piece identifiers (bundle/coil/forging IDs)

Requirements (must-have)
- Governing spec + revision (and customer addenda)
- Service environment flags (sour/low temp/etc.)
- Test requirements:
  - Chemistry element list + limits
  - Tensile properties + test standard
  - Charpy temp + orientation + specimen size + acceptance rule
  - HT route + parameters required (actuals vs “per spec”)
  - Hardness scale/method + max/min + location rules
  - NDE type/acceptance if relevant

Evidence (must-have)
- MTR report date + revision
- Test lab / mill identification
- Test method references
- Trace links: furnace run/lot, melt source (when required)
- Calibration references (if your internal spec demands it for certain reports)

5) CRM queues you’ll likely want (practical set)

- Metallurgy / Materials Engineering

This gives you clean ownership and measurable cycle time per gate.
