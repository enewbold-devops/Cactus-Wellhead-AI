======================================================================
OVERVIEW
======================================================================

The Cactus WHD Azure Function App exposes six HTTP endpoints backed by
Azure Blob Storage, Azure Queue Storage, Azure OpenAI embeddings, and a local
LanceDB vector store (or Azurite emulators for storage in local dev).

  Base URL (local):  http://localhost:7071/api
  Auth level:        ANONYMOUS (no API key required)

All responses are:
  Content-Type: application/json
  Encoding:     UTF-8
  Body format:  JSON array [] or object on success, JSON object {"error":"..."} on failure

HTTP methods supported: GET (routes 1-3, 5-6) and POST (route 4).

Two internal Azure Queue trigger functions handle asynchronous processing:
  mtr_intake_processor    — Docling PDF extraction; triggered by mtr-intake-queue
  mtr_vectorize_processor — Azure OpenAI embeddings + LanceDB write + gate validation;
                            triggered by mtr-vectorize-queue

  -  -------------------------------------  ------  ----------------------------------------
  1  GET /api/cms/providers                 GET     Full approved-providers list (JSON array)

  5  GET /api/mtr/{case_id}/status          GET     MTR case processing status record (JSON object)
  6  GET /api/mtr/{case_id}/validation      GET     Gate results + validation report (JSON object)

     mtr_intake_processor    — Queue trigger on mtr-intake-queue

     mtr_vectorize_processor — Queue trigger on mtr-vectorize-queue
                               Generates Azure OpenAI embeddings, writes to LanceDB,
                               runs Gate 0/1 validation, writes validation.json to blob

ROUTE 1 — GET /api/cms/providers
======================================================================

Description:
  Returns the complete Cactus WHD approved sub-supplier / provider list
  from cms_approved_providers.json in the blob container.

  Each record represents one approved provider for one process code at
  one physical site. A single company with multiple sites or multiple
  qualified process codes will appear as multiple records.

URL:
  http://localhost:7071/api/cms/providers

Query Parameters:
  None

Request Headers:
  None required. Optionally include Accept: application/json.

Success Response:
  HTTP 200 OK
  Content-Type: application/json

  Body: JSON array of provider objects.

  Record schema:
    {
      "provider_id":       integer   — unique sequential ID in the dataset
      "supplier_name":     string    — company name as it appears on approval record
      "site_address":      string    — street address of the qualified site
      "site_city":         string    — city (may be blank if flagged for manual review)
      "site_state":        string    — 2-letter US state code (or country abbreviation)
      "site_zip":          string    — postal/ZIP code
      "process_code":      string    — Cactus process code (e.g. "LAB-001", "CNT-002")
      "process_name":      string    — human-readable process name
      "process_category":  string    — category: "NDT", "Lab", "HeatTreat", "Coating", "Plating"
      "parent_supplier":   string    — parent company name if site operates under parent approval
      "approval_status":   string    — "Active" or "Inactive"
      "last_audit_date":   string    — ISO date string or empty string if not recorded
      "notes":             string    — free-text flags (e.g. "ADDRESS NEEDS MANUAL REVIEW",
                                       "SINGLE SOURCE — risk review required")
    }

Error Responses:
  502 {"error": "Blob storage error: <detail>"}   — cannot reach Azurite / Azure Storage
  500 {"error": "Unexpected error: <detail>"}      — unhandled server exception

  flagged = [p for p in providers if "MANUAL REVIEW" in p.get("notes", "")]
  print(f"Records needing review: {len(flagged)}")

  # Find single-source risks
  single_source = [p for p in providers if "SINGLE SOURCE" in p.get("notes", "")]
  for r in single_source:
      print(r["supplier_name"], "|", r["process_code"])

ROUTE 2 — GET /api/cms/crosswalk
======================================================================

Description:
  Returns the CMS-to-approved-process crosswalk from cms_process_crosswalk.json
  in the blob container. This is the rule matrix that maps each Cactus Master
  Specification (CMS) to its required and conditional approved-provider process
  codes, along with evidence and SOP enforcement notes.

  Use this endpoint to determine which provider process codes are mandatory
  or conditionally required for a given CMS spec before validating an MTR.

URL:
  http://localhost:7071/api/cms/crosswalk

Query Parameters:
  None

Request Headers:
  None required.

Success Response:
  HTTP 200 OK
  Content-Type: application/json

  Body: JSON array of crosswalk objects.

  Record schema:
    {
      "cms_spec":                  string    — CMS identifier (e.g. "CMS-002", "CMS-305")
      "material_scope":            string    — plain-English material/scope description
      "mandatory_process_codes":   string[]  — process codes always required
      "conditional_process_codes": string[]  — process codes required per PO/EPS flowdown
      "conditional_trigger":       string|null — describes when conditional codes activate
      "typical_mtr_evidence":      string[]  — list of required MTR data fields
      "sop_notes":                 string[]  — SOP enforcement notes and risk flags
    }

Error Responses:
  502 {"error": "Blob storage error: <detail>"}
  500 {"error": "Unexpected error: <detail>"}

---
Example — Python (requests)
---

  import requests

  BASE_URL = "http://localhost:7071/api"

  def get_crosswalk() -> list[dict]:
      resp = requests.get(f"{BASE_URL}/cms/crosswalk", timeout=30)
      resp.raise_for_status()
      return resp.json()

  crosswalk = get_crosswalk()

  # Build a lookup dict keyed by cms_spec for fast access
  crosswalk_map = {entry["cms_spec"]: entry for entry in crosswalk}

  # Resolve required codes for a given material spec
  def get_required_codes(cms_spec: str) -> dict:
      entry = crosswalk_map.get(cms_spec)
      if not entry:
          raise ValueError(f"Unknown CMS spec: {cms_spec}")
      return {
          "mandatory": entry["mandatory_process_codes"],
          "conditional": entry["conditional_process_codes"],
          "trigger": entry["conditional_trigger"],
      }

  # Example: what does CMS-305 require?
  codes = get_required_codes("CMS-305")
  print("CMS-305 mandatory:", codes["mandatory"])
  print("CMS-305 conditional:", codes["conditional"])

  # List all specs that require LAB-001
  lab_required = [e["cms_spec"] for e in crosswalk
                  if "LAB-001" in e["mandatory_process_codes"]]
  print("Specs requiring LAB-001:", lab_required)

  # Validate a provider against a resolved CMS rule
  def validate_provider_for_cms(provider_process_code: str, cms_spec: str) -> bool:
      entry = crosswalk_map.get(cms_spec, {})
      all_codes = (entry.get("mandatory_process_codes", []) +
                   entry.get("conditional_process_codes", []))
      return provider_process_code in all_codes

ROUTE 3 — GET /api/cms/chunks?cms_number=<CMS-XXX>
======================================================================

Description:
  Returns all parsed chunk records from the cms_chunks.jsonl JSONL file
  in the cms-specs/ subfolder of the blob container, filtered to records
  where doc.cms_number matches the given cms_number parameter.

  Chunk records represent extracted sections of CMS specification PDFs.
  Each chunk includes the CMS document metadata (doc) and a specific
  text segment with section context (chunk).

  Use this endpoint to:
    - Retrieve the full text content of a specific CMS spec for display
    - Search within a CMS spec's extracted sections
    - Feed spec text into an LLM/AI pipeline for MTR validation reasoning
    - Build a spec viewer by section_path or canonical_section

URL:
  http://localhost:7071/api/cms/chunks?cms_number=CMS-002

Query Parameters:
  NAME          TYPE    REQUIRED  DESCRIPTION
  cms_number    string  YES       The CMS spec number to retrieve chunks for.
                                  Must match exactly (case-sensitive).
                                  Examples: "CMS-002", "CMS-004", "CMS-107",
                                            "CMS-118", "CMS-303", "CMS-305"

Success Response:
  HTTP 200 OK
  Content-Type: application/json

  Body: JSON array of chunk objects (may be empty [] if no match found).

  Record schema:
    {
      "doc": {
        "cms_number":     string  — CMS spec number (e.g. "CMS-002")
        "revision":       string  — revision letter/number (e.g. "L")
        "effective_date": string  — effective date string (e.g. "10/18/2024")
        "title":          string  — document title
        "source_file":    string  — source PDF filename (e.g. "CMS-002.pdf")
      },
      "chunk": {
        "chunk_id":          string    — unique chunk identifier
        "type":              string    — chunk type (typically "text")
        "section_path":      string[]  — hierarchical section breadcrumb
        "page_start":        integer   — PDF page where chunk begins (1-based)
        "page_end":          integer   — PDF page where chunk ends (1-based)
        "text":              string    — extracted text content of the chunk
        "canonical_section": string    — normalised section label:
                                         "scope", "references", "heat_treatment",
                                         "mechanical_properties", "inspection",
                                         "nde", "other", "root"
        "params":            object[]  — extracted numeric parameters with
                                         lo, hi, unit, context fields
      }
    }

Error Responses:
  400 {"error": "Missing required query parameter: cms_number (e.g. ?cms_number=CMS-002)"}
                           — cms_number param was not provided
  502 {"error": "Blob storage error: <detail>"}
  500 {"error": "Unexpected error: <detail>"}

Valid cms_number values (as of 2026-03-02):
  CMS-002   Base requirements for forgings and wrought products
  CMS-004   Charpy / CVN impact framework
  CMS-107   4140 low-alloy steel
  CMS-118   4340 low-alloy steel
  CMS-303   17-4PH NACE route
  CMS-305   Alloy 718 / API 6ACRA / NACE route

  import requests

  BASE_URL = "http://localhost:7071/api"

  def get_cms_chunks(cms_number: str) -> list[dict]:
      resp = requests.get(
          f"{BASE_URL}/cms/chunks",
          params={"cms_number": cms_number},
          timeout=30,
      )
      resp.raise_for_status()
      return resp.json()

  # Retrieve all CMS-002 chunks
  chunks = get_cms_chunks("CMS-002")
  print(f"Total CMS-002 chunks: {len(chunks)}")

  # Show document metadata from the first chunk
  if chunks:
      doc = chunks[0]["doc"]
      print(f"Spec: {doc['cms_number']} Rev {doc['revision']} ({doc['effective_date']})")

  # Filter to heat treatment sections only
  ht_chunks = [c for c in chunks if c["chunk"]["canonical_section"] == "heat_treatment"]
  for c in ht_chunks:
      print(f"\n--- {c['chunk']['section_path']} (p{c['chunk']['page_start']}) ---")
      print(c["chunk"]["text"][:300])

  # Filter to scope section
  scope_chunks = [c for c in chunks if c["chunk"]["canonical_section"] == "scope"]
  for c in scope_chunks:
      print(c["chunk"]["text"])

  # Extract all chunks with numeric parameters
  param_chunks = [c for c in chunks if c["chunk"]["params"]]
  for c in param_chunks:
      for param in c["chunk"]["params"]:
          print(f"  [{c['chunk']['canonical_section']}] lo={param.get('lo')} hi={param.get('hi')} unit={param.get('unit')}")

  # Concatenate all text for full-spec LLM ingestion
  full_text = "\n\n".join(c["chunk"]["text"] for c in chunks)
  print(f"\nFull spec text length: {len(full_text)} chars")

  import requests

  BASE_URL = "http://localhost:7071/api"

  def validate_mtr_provider(cms_spec: str, provider_process_code: str, provider_name: str) -> dict:
      """
      Cross-reference a provider process code against the CMS crosswalk
      and confirmed approved-providers list.
      Returns a dict with validation outcome.
      """
      # 1) Check crosswalk — is the process code relevant to this CMS?
      crosswalk = requests.get(f"{BASE_URL}/cms/crosswalk", timeout=30).json()
      crosswalk_map = {e["cms_spec"]: e for e in crosswalk}
      spec_entry = crosswalk_map.get(cms_spec)
      if not spec_entry:
          return {"valid": False, "reason": f"Unknown CMS spec: {cms_spec}"}

      all_valid_codes = (spec_entry["mandatory_process_codes"] +
                         spec_entry["conditional_process_codes"])
      if provider_process_code not in all_valid_codes:
          return {
              "valid": False,
              "reason": f"{provider_process_code} is not applicable to {cms_spec}",
          }

      # 2) Check approved providers — is the supplier + code approved?
      providers = requests.get(f"{BASE_URL}/cms/providers", timeout=30).json()
      matches = [
          p for p in providers
          if p["process_code"] == provider_process_code
          and p["supplier_name"].lower() == provider_name.lower()
          and p["approval_status"] == "Active"
      ]
      if not matches:
          return {
              "valid": False,
              "reason": f"{provider_name} not found as an Active approved provider for {provider_process_code}",
          }

      # 3) Check notes for flags
      flags = [p["notes"] for p in matches if p["notes"]]
      return {
          "valid": True,
          "matched_sites": len(matches),
          "flags": flags,
      }

  # Usage
  result = validate_mtr_provider("CMS-002", "LAB-001", "Accu-Test Labs")
  print(result)
  # -> {"valid": True, "matched_sites": 1, "flags": []}

  result = validate_mtr_provider("CMS-305", "CCS-612", "Houston Plating & Coatings")
  print(result)
  # -> {"valid": True, "matched_sites": 1, "flags": ["ADDRESS NEEDS MANUAL REVIEW; SINGLE SOURCE — risk review required"]}

ROUTE 4 — POST /api/mtr/intake
======================================================================

Description:
  Accepts an MTR document upload via multipart/form-data. Immediately
  stores the original file to the cactus-mtr blob container, writes an
  initial status.json record, and enqueues a processing message on
  mtr-intake-queue. Returns a case_id instantly without waiting for
  Docling processing to complete.

  Docling conversion and chunking run asynchronously via the
  mtr_intake_processor queue trigger. Poll GET /api/mtr/{case_id}/status
  to check when processing is complete.

URL:
  http://localhost:7071/api/mtr/intake

Method: POST

Request Format:
  Content-Type: multipart/form-data

  Form fields:
    file    (required)  The MTR document file. Field name must be "file".

Accepted File Types:
  Extension    MIME type
  ----------   ----------------------------------------
  .pdf         application/pdf
  .docx        application/vnd.openxmlformats-officedocument.wordprocessingml.document
  .xlsx        application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
  .jpg .jpeg   image/jpeg
  .png         image/png
  .tif .tiff   image/tiff

Success Response:
  HTTP 201 Created
  Content-Type: application/json

  Body:
    {
      "case_id":      string   — UUID for the MTR validation case
      "status":       string   — always "queued" on success
      "filename":     string   — original filename as uploaded
      "submitted_at": string   — ISO-8601 UTC timestamp
      "status_url":   string   — relative URL to poll for processing status
    }

Error Responses:
  400 {"error": "Missing required form field: 'file'..."}    — no file in request
  400 {"error": "Uploaded file is empty."}                   — zero-byte file
  415 {"error": "Unsupported file type '.xyz'..."}            — disallowed extension
  502 {"error": "Blob storage error: <detail>"}              — Azurite/storage issue
  500 {"error": "Unexpected error: <detail>"}                — unhandled exception

  Degraded mode (202 Accepted):
  If the file was stored but the queue send failed:
    {
      "case_id": "...",
      "status":  "queue_error",
      "warning": "File accepted but could not be enqueued for processing...",
      "status_url": "/api/mtr/{case_id}/status"
    }

Blob Paths Written (cactus-mtr container):
  mtr/{case_id}/raw/{filename}          — original file as received
  mtr/{case_id}/status.json             — initial status record (status: queued)

Example — Python (submit + poll)
---

  import requests, time

  BASE_URL = "http://localhost:7071/api"

  def submit_and_wait(file_path: str, poll_interval: int = 5, timeout: int = 300) -> dict:
      """Submit an MTR and poll until processing is complete or failed."""
      # 1. Submit
      with open(file_path, "rb") as f:
          resp = requests.post(
              f"{BASE_URL}/mtr/intake",
              files={"file": (file_path.split("/")[-1], f)},
              timeout=60,
          )
      resp.raise_for_status()
      result = resp.json()
      case_id = result["case_id"]
      status_url = f"{BASE_URL}/mtr/{case_id}/status"
      print(f"Submitted case_id={case_id}, status=queued")

      # 2. Poll
      elapsed = 0
      while elapsed < timeout:
          time.sleep(poll_interval)
          elapsed += poll_interval
          status = requests.get(status_url, timeout=30).json()
          print(f"  [{elapsed}s] status={status['status']}")
          if status["status"] in ("complete", "failed"):
              return status
      raise TimeoutError(f"Processing did not complete within {timeout}s")

  result = submit_and_wait("heat_123456_mtr.pdf")
  print(f"Final status: {result['status']}")
  if result["status"] == "complete":
      print(f"Chunks: {result['chunk_count']}")
      print(f"Artifacts: {result['artifacts']}")

ROUTE 5 — GET /api/mtr/{case_id}/status
======================================================================

Description:
  Returns the current processing status record for a given MTR case.
  The case_id is the UUID returned by POST /api/mtr/intake.

  Status transitions (full lifecycle):

    queued → processing → complete → vectorizing → validation_ready
                                                 → under_review      (review_flags present)
                                                 → vectorize_failed  (embedding/LanceDB error)
                        → failed        (Docling processing error)
                        → queue_error   (file stored, queue send failed)

  Poll until one of these terminal statuses is reached:
    validation_ready  accepted  accepted_with_conditions
    rejected  deviation_required  under_review  failed  vectorize_failed  queue_error

URL:
  http://localhost:7071/api/mtr/{case_id}/status

Method: GET

Path Parameters:
  NAME       TYPE    REQUIRED  DESCRIPTION
  case_id    string  YES       UUID returned by POST /api/mtr/intake

Success Response:
  HTTP 200 OK
  Content-Type: application/json

  Status record schema:
    {
      "case_id":          string        — UUID for the MTR validation case
      "status":           string        — see status lifecycle above
      "filename":         string        — original filename
      "submitted_at":     string        — ISO-8601 UTC submission timestamp
      "completed_at":     string|null   — ISO-8601 UTC Docling completion timestamp
      "vectorized_at":    string|null   — ISO-8601 UTC vectorization completion timestamp

  import requests

  BASE_URL = "http://localhost:7071/api"

  def get_mtr_status(case_id: str) -> dict:
      resp = requests.get(f"{BASE_URL}/mtr/{case_id}/status", timeout=30)
      if resp.status_code == 404:
          raise ValueError(f"Unknown case: {case_id}")
      resp.raise_for_status()
      return resp.json()

  TERMINAL = {"validation_ready", "under_review", "accepted", "accepted_with_conditions",
              "rejected", "deviation_required", "failed", "vectorize_failed", "queue_error"}

  def poll_to_terminal(case_id: str, interval: int = 5, timeout: int = 600) -> dict:
      url = f"{BASE_URL}/mtr/{case_id}/status"
      elapsed = 0
      while elapsed < timeout:
          status = requests.get(url, timeout=30).json()
          print(f"  [{elapsed}s] {status['status']}")
          if status["status"] in TERMINAL:
              return status
          time.sleep(interval)
          elapsed += interval
      raise TimeoutError("Pipeline did not reach terminal status")

  result = poll_to_terminal("3fa85f64-5717-4562-b3fc-2c963f66afa6")
  print(f"Final status: {result['status']}")
  if result["status"] == "validation_ready":
      print(f"CMS set: {result.get('resolved_cms_set')}")
      print(f"LanceDB table: {result.get('lancedb_table')}")
      print(f"Validation: {result['artifacts'].get('validation_json')}")

INTERNAL — QUEUE TRIGGER: mtr_intake_processor
======================================================================

This function is not an HTTP endpoint. It is triggered automatically by
Azure Functions when a message appears on the mtr-intake-queue queue.

Queue name: mtr-intake-queue
Poison queue: mtr-intake-queue-poison (auto-created by Functions runtime)
Connection: AzureWebJobsStorage

Message schema (JSON):
  {
    "case_id":      string   — UUID of the MTR case
    "filename":     string   — original filename (for raw blob path resolution)
    "suffix":       string   — Docling file suffix (e.g. ".pdf", ".docx")
    "submitted_at": string   — ISO-8601 UTC submission timestamp
  }

Processing steps:
  1. Update status.json → "processing"
  2. Read raw file bytes from mtr/{case_id}/raw/{filename}
  3. Run PDFProcessor.process_from_bytes(file_bytes, suffix)
  4. Export markdown: document.export_to_markdown()
  5. Run PDFProcessor.process_to_structured() → structured JSON
  6. Write mtr/{case_id}/processed/{case_id}.md
  7. Write mtr/{case_id}/processed/{case_id}_chunks.jsonl
  8. Write mtr/{case_id}/processed/{case_id}_structured.json
  9. Update status.json → "complete" with chunk_count and completed_at
  10. Enqueue message on mtr-vectorize-queue to trigger AI vectorization
      (failure to enqueue is non-fatal — logs a warning; status remains "complete")
     On any exception in steps 1-9: update status.json → "failed" with error message

Blob paths produced (cactus-mtr container):
  mtr/{case_id}/raw/{filename}                   — original file (written at intake)
  mtr/{case_id}/status.json                      — status record (updated throughout)
  mtr/{case_id}/processed/{case_id}.md           — Docling markdown output
  mtr/{case_id}/processed/{case_id}_chunks.jsonl — one JSON object per line per chunk
  mtr/{case_id}/processed/{case_id}_structured.json — full structured doc + chunk array

Structured JSON schema:
  {
    "case_id":       string,
    "filename":      string,
    "processed_at":  string,       — ISO-8601 UTC
    "doc_metadata":  {
      "page_count":   integer,
      "source_file":  string
    },
    "chunks": [
      {
        "chunk_index": integer,
        "text":        string,
        "meta":        object      — serialisable Docling chunk metadata
      }, ...
    ]
  }

======================================================================
INTERNAL — QUEUE TRIGGER: mtr_vectorize_processor
======================================================================

This function fires automatically when mtr_intake_processor enqueues a message
on mtr-vectorize-queue after successful Docling extraction.

Queue name: mtr-vectorize-queue
Poison queue: mtr-vectorize-queue-poison (auto-created by Functions runtime)
Connection: AzureWebJobsStorage
batchSize: 1  |  visibilityTimeout: 300s  |  maxDequeueCount: 5

Message schema (JSON):
  {
    "case_id":      string   — UUID of the MTR case
    "filename":     string   — original filename
    "submitted_at": string   — ISO-8601 UTC submission timestamp
  }

Processing steps:
  1.  Parse queue message — extract case_id
  2.  Update status.json → "vectorizing"
  3.  Load structured JSON from mtr/{case_id}/processed/{case_id}_structured.json
  4.  Resolve CMS spec set (regex on chunk text against known CMS identifiers)
  5.  Classify chunks by semantic class (chemistry, charpy, hardness, mechanical,
      heat_treatment, ndt, identity, other) using regex pattern matching
  6.  Extract structured fields per chunk (element values, test results, heat numbers)
  7.  Build text_for_embed string per chunk (section + extracted fields + raw text)
  8.  Batch embed all chunks via Azure OpenAI text-embedding-3-large (3072 dims)
      Batch size: 16 chunks per API call
  9.  Write chunk rows to LanceDB per-case table (threading.Lock + FileLock mutex)
  10. Gate 0 check — completeness: verify heat#, PO#, chemistry, mechanicals, hardness present
  11. Gate 1 check — identity: confirm heat number matches PO reference, grade resolved
  12. Write validation.json to mtr/{case_id}/processed/{case_id}_validation.json
      Update status.json → "validation_ready" | "under_review" (if review_flags present)
     On any exception: update status.json → "vectorize_failed" with error message

Blob paths produced (cactus-mtr container):
  mtr/{case_id}/processed/{case_id}_validation.json — gate results + chunk classifications

Azure OpenAI configuration:
  Model:      text-embedding-3-large
  Dimensions: 3072 (full, not truncated)
  Env vars:   AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_API_KEY, AZURE_OPENAI_EMBED_DEPLOYMENT
  API version: 2024-02-01

LanceDB configuration:
  Path:       LANCEDB_PATH env var (default: vectordb_lancedb/ in workspace root)
  Tables:     cms_spec_chunks  — CMS specification knowledge base (seeded separately)
              mtr_{case_id_underscored}  — per-case embedded chunk table
              mtr_case_registry          — flat registry of all case metadata
  Concurrency: threading.Lock (in-process) + FileLock on .lancedb_write.lock sentinel

Validation JSON schema:
  {
    "case_id":          string,
    "validated_at":     string,      — ISO-8601 UTC
    "resolved_cms_set": string[],   — e.g. ["CMS-002", "CMS-107"]
    "gates": {
      "gate_0": {
        "status":         "pass" | "fail" | "pending",
        "missing_fields": string[]   — populated if status is "fail"
      },
      "gate_1": {
        "status":         "pass" | "fail" | "pending",
        "heat_number":    string | null,
        "grade_resolved": string | null,
        "po_reference":   string | null
      },
      "gate_2": { "status": "pending" },   — CTQ chemical/mechanical limit check (future)
      "gate_3": { "status": "pending" },   — provider correlation check (future)
      "gate_4": { "status": "open" }       — record lock (requires human disposition)
    },
    "chunk_classifications": [
      {
        "chunk_index":    integer,
        "semantic_class": string,     — "chemistry" | "charpy" | "hardness" | "mechanical"
                                        | "heat_treatment" | "ndt" | "identity" | "other"
        "confidence":     "high" | "medium" | "low",
        "needs_review":   boolean,
        "extracted_fields": object    — key-value pairs extracted for this class
      }, ...

ERROR HANDLING REFERENCE
======================================================================

  HTTP STATUS  MEANING                          ACTION FOR CALLER
  -----------  -------------------------------- ----------------------------------------
  200          Success (GET)                    Parse response body as JSON
  201          Created (POST /mtr/intake)       Parse case_id; begin polling status URL
  202          Accepted — degraded              File stored; queue send failed; check status
  400          Bad request (missing param)      Fix query string or form field before retrying
  404          Not found                        case_id is unknown or invalid
  415          Unsupported media type           File extension not in allowed set
  500          Unhandled server error           Log and alert; do not retry immediately
  502          Blob/queue storage unreachable   Check Azurite is running; retry with backoff

  All error responses follow the schema: {"error": "<message string>"}

  Caller-side recommended pattern:
    1. POST /mtr/intake:   check status_code == 201; extract case_id from body
    2. GET status:         poll until status == "complete" or "failed"
    3. For 400/415:        surface the error.error message to the user
    4. For 404:            case_id not recognised — check UUID is correct
    5. For 502:            retry up to 3 times with 2s exponential backoff
    6. For 500:            log full response body to error tracking
